# ВышКат: Система учёта парка кикшеринга



Консольное приложение для управления парком транспортных средств и инвентаря. Реализует учёт техники, автоматический техосмотр перед приёмкой, расчёт энергопотребления и фильтрацию по характеристикам для новичков.



## Как запустить



### 1. Локальный запуск (требуется .NET 8/10 SDK)



Сборка и запуск интерактивного меню (по умолчанию):

```bash

dotnet run

```



Запуск автоматической демонстрации всех сценариев из ТЗ:

```bash

dotnet run -- --demo

```



Справка:

```bash

dotnet run -- --help

```



### 2. Запуск юнит-тестов



```bash

dotnet test

```

## Архитектурные решения и SOLID



### 1. Какой принцип SOLID применён наиболее явно и где?



**Open-Closed Principle (OCP) и Dependency Inversion Principle (DIP).**



- **DIP:** Класс `Park` зависит от абстракции `IServiceCenter`, а не от конкретной реализации `ServiceCenter`. Зависимость внедряется через конструктор (Constructor Injection).

- **OCP:** Класс `VehicleFactory` использует словарь делегатов (`Dictionary<int, Func<...>>`). Добавление нового вида транспорта требует добавления только одной строки в словарь и одного приватного метода-создателя. Классы `Park`, `InteractiveRunner` и `EnergyCalculator` при этом не изменяются.



### 1.1 Общее применение принципов SOLID



**S — Single Responsibility (Единственная ответственность)**

Чёткое разделение на слои внутри домена: интерфейсы (`Domain.Interfaces`) задают контракты, модели (`Domain.Vehicles`, `Domain.Items`) хранят данные об объектах, сервисы (`Domain.Services` — `Park`, `EnergyCalculator`, `ServiceCenter`) реализуют бизнес-логику, а фабрики отвечают за создание объектов. Ввод данных изолирован в `ConsoleHelper`, а раннеры управляют потоком взаимодействия с пользователем.



**O — Open/Closed (Открытость/закрытость)**

Реализован через фабрики со словарем дескрипторов в `VehicleFactory` и `InventoryItemFactory`. Добавление нового транспорта (например, `Monowheel`) требует лишь добавления строки в словарь и метода-создателя. Классы `Park`, `EnergyCalculator` и раннеры **не изменяются ни на байт**.



**L — Liskov Substitution (Подстановка)**

Формально принцип чаще всего нарушается при наследовании классов, но в архитектуре он соблюдается на уровне интерфейсов.



**I — Interface Segregation (Разделение интерфейса)**

Вместо одного «божественного» интерфейса созданы минимальные роли: `IEnergyConsumer` (только энергия), `IBeginnerFriendly` (только оценка простоты). Классы реализуют только нужные им интерфейсы (например, `Bicycle` не имеет энергии, а `Helmet` не является транспортом).



**D — Dependency Inversion (Инверсия зависимостей)**

Высокоуровневый `Park` зависит от абстракции `IServiceCenter`, а не от конкретной реализации. Зависимость внедряется через конструктор. В `Program.cs` используется DI-контейнер (`Microsoft.Extensions.DependencyInjection`) для автоматической сборки графа зависимостей.



### 2. Какой принцип сознательно ограничен / «почти нарушен» и почему это приемлемо?



**Interface Segregation Principle (ISP) / Single Responsibility Principle (SRP) в `VehicleFactory`.**



Фабрика напрямую запрашивает данные у пользователя через `ConsoleHelper`. Строго говоря, фабрика не должна знать о UI. Однако для консольного CLI-приложения создание отдельной абстракции `IUserInput` с последующим внедрением её в фабрику является классическим **overengineering**. Это сознательный компромисс, который сохраняет код читаемым, при этом доступным к расширению.



### 3. Что сломается (или не сломается) при добавлении нового вида транспорта?



При добавлении нового транспорта (например, `Monowheel : IVehicle, IEnergyConsumer`):



- **НЕ сломается и НЕ потребует изменений:** `Park`, `EnergyCalculator`, `InteractiveRunner`, `DemoRunner`, `ServiceCenter`. Они работают исключительно через интерфейсы.

- **Потребует минимального изменения:** Только `VehicleFactory` (добавление записи в словарь и метода `CreateMonowheel`). Это прямое доказательство соблюдения OCP.



### 4. Какой тест фиксирует правило техосмотра и как подменяется зависимость?



Тест `Park_AddVehicle_WhenServiceCenterRejects_ShouldNotAdd` в проекте `VyshKat.Tests`.



**Механизм подмены:** Создаётся класс `FakeRejectingServiceCenter`, реализующий `IServiceCenter` и всегда возвращающий `false`. Этот фейк передаётся в конструктор `Park`. Тест подтверждает, что `Park` корректно отклоняет транспорт и не добавляет его во внутреннюю коллекцию, не завися при этом от реальной логики `ServiceCenter`.



### 5. Роль ИИ в разработке



ИИ использовался как интеллектуальный ассистент для разбора концепций и структур языка C#.



- **Что сделал ИИ:** Предлагал паттерны и синтаксические решения, неочевидные на текущем уровне владения языком (например, использование `using var` для `ServiceProvider`, объяснение *deferred execution* в LINQ, корректная обработка прерываний `Console.CancelKeyPress`); писал большую часть Unit-тестов; занимался форматированием markdown данного файла README.

- **Что сделал разработчик:** Самостоятельно спроектировал общую архитектуру доменной модели, продумал границы ответственности классов, проанализировал каждое предложение ИИ, писал с нуля и адаптировал код от ИИ под конкретные требования ТЗ. ИИ ни в коем случае не генерировал итоговый код "вслепую".

## Структура проекта



- `VyshKat.Domain.Interfaces` — контрактная часть (интерфейсы)

- `VyshKat.Domain.Vehicles` / `Items` — доменные модели с инкапсулированной валидацией

- `VyshKat.Domain.Services` — бизнес-логика (`Park`, `EnergyCalculator`, `ServiceCenter`)

- `VyshKat.Domain.Factories` — фабрики

- `VyshKat.Utils` — утилиты для безопасного консольного ввода

- `VyshKat.Tests` — модульные тесты (xUnit)
